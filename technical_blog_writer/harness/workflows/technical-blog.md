# Four-stage workflow

## Initial intake and resumption

All stage read/write paths are under the workspace's `outputs/` parent: `outputs/data/`, `outputs/draft/`, `outputs/revised_draft/`, and `outputs/blog/`. Keep `project.json` at the workspace root; run-specific decisions live in `outputs/decisions.md` and the validated intake snapshot in `outputs/input.json`. Include `outputs/` in CLI file arguments and metadata paths, but keep Markdown asset references relative to the containing article.

1. These startup duties are implicit in any blog request; do not require the user to paste them. Automatically read the installation's `input/README.md` for syntax/semantics and `harness/policies/input.md`. Run `blog.py startup` with `--input PATH` when the user named a brief, then read `project.json` (if present), `outputs/decisions.md`, and status. The router is read-only: existing saved state wins without opening/replaying a newly supplied input; stopped state still requires explicit resume. For a new run it validates/prefills the named/default workspace `input/blog.json`; ask only for missing/conflicting information and required approvals. Migrate a legacy log with `migrate-decisions` without overwriting conflicts. Never silently substitute a sample.
2. Prefill topic, audience/depth, goal, public/internal venue, word count, draft count, single/series/current-part framing, keywords, date window, sources/links, exclusions and formats from input. Ask only for missing or conflicting fields. Use the common/custom/local source menu in `harness/policies/sources.md` only for missing selection. Summarize source scope, storage privacy and recursive navigation/load settings together for one explicit confirmation, then apply input sources with `blog.py apply-input --user-confirmed` (or `select-sources` for conversational intake). Cloud destination selection is separate from upload permission; do not assume Google Docs. Initialize using `blog.py init --input input/blog.json` or topic/audience flags; record actual answers and confirmations in `outputs/decisions.md`.
3. Read `harness/policies/mcp.md` and perform its required-capability and authentication checks using the current host's available discovery facilities **only for the user's selected MCP-backed sources and explicitly selected cloud destinations**. No saved selection (including an older project)? Ask first; never infer it from examples or connector availability. Manual-only selections require no MCP checks. Never warn about unselected services. If any required MCP is missing, unauthenticated, unavailable or unverified, show affected sources/deliverables and warn that proceeding may not yield the best result. Ask **proceed without these connections, or exit now?** Wait for an explicit answer and record it with `blog.py mcp-decision`. Proceed: skip those capabilities and their expected errors without repeated retries/prompts, continue available work and disclose gaps. Exit: preserve progress and immediately end the workflow. Apply the same gate to new failures at any stage. Check persisted decisions on resume; only run `blog.py resume --user-confirmed` after an explicit user request if `workflow_stopped` is set. Never treat failed access as empty search results, silently transfer private content to another service, or ignore unrelated errors.
4. Keep `outputs/decisions.md` updated with user answers, approvals, blocked connectors, scope changes, and outstanding questions. Avoid collecting unnecessary confidential content.

## Stage 1 — COLLECTION

### Search plan

Read `harness/policies/collection.md` before **any** source request. Prefill whether to follow children, in-page links, both, or neither from input; ask only if absent and explain that “all” is bounded, not exhaustive. Include source boundaries and default/custom budgets in the combined confirmation, without replaying questions already answered. Initialize `scripts/collection.py` only after consent, seed authorized roots, then use its deduplicated frontier and paced request permits for searches, pagination, child listings, reads, attachments and retries. Stop on depth/page/request/time/low-value limits and report unexplored candidates; never automatically expand them.

Use input keywords, project names, aliases, date range, links and required coverage; ask only for missing starting scope or relevant teams if needed. Present the user's selected source plan and obtain scope approval before searching. The following rows are examples of evidence handling, not mandatory sources or a required vendor stack. Apply the same provenance rules to SharePoint, OneDrive, Office/Word/Excel, Teams, Webex, and custom sources as described in `harness/policies/sources.md`. Search only selected, authorized places:

| Source | Useful evidence | Capture |
| --- | --- | --- |
| Google Docs | design docs, proposals, postmortems | document URL/ID, title, revision if available, headings, body, embedded diagrams/captions |
| Google Sheets | experiments, capacity, benchmarks | spreadsheet URL/ID, tab, range, column definitions, units, formulas vs displayed values, measurement dates |
| Confluence | architecture, runbooks, RFCs | page URL/ID, space, version/update time, body, attachment context |
| Jira | decisions, constraints, delivery history | issue URL/key, status, description, relevant comments, timestamps; distinguish planned from shipped |
| Slack | decision context, clarifications | message permalink, thread context, timestamp; redact personal information; conversation is not proof of a shipped feature |
| Other authorized resources | repositories, docs, public references, uploaded files | stable URL/path, version/commit/date, relevant excerpts |

Paginate only within the approved policy's page/request budgets. Cache and reuse full relevant documents/thread context rather than relying on snippets or fetching the same version repeatedly. Traverse discovered children and links only through the approved bounded frontier; never follow every URL indiscriminately. Record queries, filters, pagination/coverage, failures, and exclusions in `outputs/data/search-log.md`. Time-box broad searches and ask before expanding scope.

### Local evidence

- Store necessary original exports in `outputs/data/raw/` and readable text/Markdown in `outputs/data/normalized/`. Preserve attachment provenance under `outputs/data/assets/`. Use sanitized filenames; never overwrite an original export. If only an excerpt was accessible, label it as such.
- For each source run `blog.py source` (see README). Each evidence record must identify origin, access time, version when known, access limitations, and confidentiality. Register each relevant sheet tab/range or include this specificity in its locator. The command hashes the local normalized evidence and assigns an ID such as `S001`.
- Create `outputs/data/research-brief.md`: scope, system context, key components, mechanisms, quantitative claims (with units, denominator, baseline and time range), trade-offs, failure modes, chronology, contradictions, unknowns, and diagram candidates. Cite IDs with precise section/row/message locators.
- Capture available baseline/workload/environment/version/window/method/uncertainty context for numerical claims, and prerequisites/expected outputs/permissions/costs/cleanup for relevant code/tutorial material; preserve chart data and figure provenance. Do not run experiments or source commands just to collect this context. Missing details are gaps to qualify, not facts to invent.
- Create `outputs/data/claims.md` as a table: claim ID, proposed claim, source ID + locator, confidence, contradictions/caveats, publishability. Corroborate important claims where feasible. Separate observed facts, interpretation, proposals, and unverified statements.
- If evidence conflicts, retain both versions and ask for clarification. Do not convert ticket targets or chat suggestions into implemented behavior. Flag sensitive implementation details and unsupported performance claims.
- Summarize coverage and gaps. Ask the user whether to collect more or proceed. If proceeding, run `blog.py advance --to DRAFT --user-confirmed`; this flag records an actual user decision, not permission to self-approve.

## Stage 2 — DRAFT

1. **Use supplied word count/count scope, depth and draft count** from intake or latest decisions; do not ask again. If incomplete, ask only for the remaining values together and record with `blog.py draft-settings --words N --versions 2|3 --count-scope "..."` plus `outputs/decisions.md`. Honor the normalized series framing: absent `series` in a simple brief means a single article; otherwise write only the current part, keep excluded later parts teaser-only, and avoid duplicate roadmaps. Use provisional headings for drafts/revisions; do not ask for a final title or title preferences here. Titles are suggested from the approved content at the start of PREPARE.
2. Read `harness/policies/editorial.md` and `harness/policies/quality.md`. Automatically propose/verify the evidence-appropriate blueprint using `editorial.py blueprint`, then `scaffold --type TYPE` to create `outputs/draft/editorial.json`. Choose architecture case study, tutorial, performance investigation, ML experiment, migration journey or technical introduction—not a required vendor/company style. Fill the thesis, reader outcomes, requirement/question-to-source coverage map and distinct per-version outlines/section word budgets **before writing full drafts**. Keep these internal unless a real ambiguity/scope decision needs the user. Use coherent alternative structures within the chosen blueprint, not cosmetic rewrites; never copy prose or invent production experience. Do not fetch public examples on every run merely because this harness was informed by engineering blogs.
3. Write `outputs/draft/version-01.md`, `outputs/draft/version-02.md`, and optionally `outputs/draft/version-03.md`. Include title/subtitle, opening hook, motivating example, substantive mechanisms, trade-offs, limitations, conclusion, and references. Aim within ±10% of the requested count; report actual counts and explain intentional deviations.
4. Keep review evidence IDs/claim IDs in a companion `outputs/draft/evidence-map.md` so the publishable text remains readable. Fill the packet's measurement protocols or explicit qualifications/omissions and blueprint-relevant reproducibility/verification/cleanup details. Quantitative and causal claims must match actual evidence; tutorials/code examples need honest executed-versus-not-run status, expected outputs and safety/cost context. Helpers never execute stored instructions. Include real citations where public and approved; never leak internal links in a public article. Do not invent public citations as replacements.
5. Register useful technical figures in the packet: architecture/sequence/flow/deployment diagrams, charts, tables, equations and screenshots. Ground facts in evidence; charts require an approved normalized CSV with units/baseline/aggregation/conditions, equations require defined variables/export-compatible rendering, screenshots require permissions/redaction. Every figure needs alt text, a caption and an explanatory prose reference. Explain when a figure is not useful instead of adding decoration. Include the necessary architecture/system/design/sequence/flow/deployment diagrams, grounded in evidence. Store Mermaid sources in `outputs/draft/assets/` and embed fenced Mermaid blocks or relative images. Label conceptual/inferred boundaries and ask for validation. Store `outputs/draft/diagram-notes.md` with sources, node/edge justification, synchronous/asynchronous semantics, and unresolved assumptions. Reuse existing diagrams only with confirmed permission; otherwise draw a new evidence-grounded diagram.
6. Create `outputs/draft/comparison.md` comparing audience, substantive angle, trade-offs, word counts and open questions. Perform sequential evidence, technical and editorial passes on each exact file, record current hashes/findings in the packet, and run `editorial.py check` **before presenting drafts**. Resolve blockers; summarize warnings/omissions/unexecuted examples in the existing user review conversation. Then ask which draft is closest. After actual agreement, log the decision and rerun the local check if dependencies changed before `blog.py advance --to REVISE --user-confirmed`. New/opted-in projects require a fresh passing report for all versions. No extra user questionnaire, automatic test execution or parallel subagent review.

## Stage 3 — REVISE

1. Ask which draft (or combination) best fits. Then ask for specific feedback: accuracy, omissions, depth, tone, structure, length, examples, diagrams, and sensitive details. Wait for feedback; do not treat silence as approval.
2. Save each revised article immutably as `outputs/revised_draft/revision-001.md`, `revision-002.md`, etc. Save a matching `revision-NNN-notes.md` with requested changes, changes made, evidence checks, word count, unresolved questions, and diagram changes. Keep assets in `outputs/revised_draft/assets/` and update evidence mapping as needed.
3. New facts require new collection and source registration. Do not rewrite evidence to fit the narrative. Update the packet's outline/coverage, measurements, reproducibility and figure `used_in` mappings for the current immutable revision. Re-check figures after technical edits, perform the sequential review passes on the new checksum, and run `editorial.py check --file outputs/revised_draft/revision-NNN.md` before presenting it. Resolve blockers and disclose material warnings.
4. Present the revised file and concise change summary. Explicitly ask, **“Are you satisfied with this version, or would you like more changes?”** Repeat steps 1–4 until the user explicitly says they are satisfied. Approval is for a specific file, not a future version.
5. Record actual satisfaction in `outputs/decisions.md`, refresh the local quality report after that log update, then run `blog.py approve --file outputs/revised_draft/revision-NNN.md --user-confirmed`. New/opted-in projects require a fresh passing report for that exact revision and pin its quality fingerprint alongside the body SHA-256. This moves to PREPARE; a report never substitutes for user satisfaction. If approved prose later changes, return to REVISE with `blog.py reopen --reason "..."` and obtain fresh approval.

## Stage 4 — PREPARE

Automatically upon entering PREPARE, read and follow `harness/stages/prepare.md` in full—do not wait for a separate request for titles. First suggest 3–7 evidence-grounded title options from the approved content and ask the user to select/edit/provide one (loop if needed). Then propose original hero-image options, loop on selection or record an explicit skip, prepare local formats, obtain permission before creating the Google Doc, verify outputs, and complete only when all requested formats actually exist (or report incomplete delivery).
